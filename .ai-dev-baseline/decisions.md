## D3 — the bare suite run is excluded from Claude Code's sandbox, without an ask rule
- date:      2026-10-06
- category:  project-delta
- unknown:   inside Claude Code's macOS sandbox the setuid /bin/ps cannot be executed, so test/run.sh cannot check what a unit leaves behind and stops before any unit (#6)
- decision:  `.claude/settings.json` lists `bash test/run.sh` in `sandbox.excludedCommands`, with no `permissions.ask` rule for it
- placement: .claude/settings.json; README "Testing shmutant"
- reason:    the owner specified the entry in #6. An excluded command still goes through the permission flow, but not through the guards a user may put on unsandboxed retries: retries turned off in their own settings, an ask rule on `Bash(dangerouslyDisableSandbox:true)`, or `permissions.blockReadsOutsideWorkingDirectories`. For that user the exclusion runs the suite unsandboxed where a retry would have been refused or prompted. The ask rule the vendor docs pair with an excluded script restores a prompt in bypassPermissions and auto modes, where the excluded command otherwise runs unprompted or under the classifier's review; in the modes that prompt for it anyway it adds nothing. The exclusion runs whatever test/run.sh and shmutant.sh hold. The [gates] test command (run under `sh -c` by the gate runner) does not match it, stays sandboxed, and stops at once with exit 2. Nor does the self-mutation command: sandboxed, its baseline aborts, every row is scored `baseline`, and it exits 1.
- alternative: `"permissions": {"ask": ["Bash(bash test/run.sh)"]}` beside the exclusion: each run approved by hand; not taken for the prompt it adds to every suite run in bypassPermissions and auto modes
- baseline-issue: n/a (agent sandbox settings are per project)

## D5 — the release procedure is a project skill over a tested script
- date:      2026-10-06
- category:  project-delta
- unknown:   #8 asks for a project-owned release command that the roadmap artifact's `release-command` marker can name. The baseline ships no `/release` skill, so each project writes its own.
- decision:
  - `.claude/skills/release/SKILL.md` (a Claude Code skill: the roadmap marker resolves for Claude, the primary here) settles the version, runs `scripts/release.sh --dry-run`, gets the operator's go-ahead, cuts, and hands off to `baseline release roll`. Only the operator can invoke it (`disable-model-invocation: true`).
  - The script holds every step. `test/release.sh` runs it against a local bare origin, with `gh`, `curl` and `sleep` stubbed. It runs in the `release` CI job (ubuntu, plus macOS under `/bin/bash` 3.2) and as the `release-test` gate (cadence `full`).
  - CI is green on origin's main head when all of these hold:
    - every check run GitHub lists there with `filter=latest` is `completed` with conclusion `success`, so `skipped` and `neutral` refuse, and at least one exists;
    - the `ci.yml` workflow has run on that SHA and each of its runs concluded `success`. A finished run means every job reported, however it is named or matrixed, so ci.yml itself is never parsed;
    - its commit statuses, if it has any, combine to `success`. With none, GitHub reports `pending`, which is ignored.
  - This "green" is stricter than the baseline's `roadmap-lib.sh branch-health`, which counts `skipped` and `neutral` as green, so `/roadmap` can announce a cut that this script then refuses. The refusal is the safe side of that disagreement: a tag is permanent, and a skipped job on the commit being tagged is a check nobody ran.
  - A pending check refuses at once; the script does not wait.
  - `CHECKSUMS` is checked by a stricter form of `sha256sum -c` that needs no `sha256sum`: it must be exactly one `<sha256>  shmutant.sh` line (lowercase hex, text mode, 78 bytes, so no NUL hides in it), and the digest must match `shmutant.sh` as committed at HEAD. The digest helper is the script's own, not `shmutant.sh`'s `_shmutant_checksum`: that one needs bash 5.3 and a file, and the script runs on macOS's bash 3.2 and hashes git blobs on stdin. Nor is it the installed baseline's `adb_sha256_stdin`: that library lives in the operator's home, not in this repository, and CI does not have it.
  - The install URL in `docs/integrating.md` must already name the tag being cut, so the docs at the tag install that release. #8 suggested substituting the version; a doc naming an older tag refuses instead. Only a whole URL ending exactly in `/shmutant.sh` counts, so `shmutant.sh.sig` or a `?query` form is never read as the install URL.
  - origin must have exactly one URL, and it and every push URL must name the same github.com repository; HTTPS userinfo is held to characters that cannot end the host. gh is pinned to github.com, and its account must be able to push there. git's own URL rewriting (`insteadOf`, `pushInsteadOf`) is the operator's configuration and is honoured; what binds the cut to GitHub's repository is GitHub-side: the API agreeing on main before the tag, and `--verify-tag` and the post-publish verification after it. A push that git reports done but origin's URL does not show is named as such.
  - The caller's exported functions and aliases, `GIT_*` repository variables, git's tracing variables, `GH_HOST`, and the shell options that change what a command does are set aside before anything is read. `GIT_ASKPASS=false` means credentials come only from a credential helper or gh's login: nothing prompts. `noexec` and `onecmd` cannot be undone from inside a script, so the skill runs the driver under `env -u SHELLOPTS -u BASHOPTS -u BASH_ENV` and takes success from its last line on stdout, not its exit status alone.
  - The report goes to stdout. A report line that cannot be written (a closed or full stdout) is counted rather than fatal, and a run that would exit 0 exits 2 instead, saying on stderr what it did: every precondition held, the release verifies, or it is published and verifies. A cut that lost a line before the tag stops there, with nothing tagged. A refusal or a failed step keeps its own exit status (1, or 2 for a failed read) whether or not its report was written. Each line is written from a subshell, so a broken pipe's SIGPIPE ends only that subshell and is counted like any other failed write; the subshell also keeps bash 3.2 from holding the unwritten line in its buffer, where the next command substitution would read it back. `--help` writes its usage the same way and exits 2 when it cannot. The URL `gh release create` prints once the release exists goes to stderr, so a failing stdout cannot fail the create of a release that was made.
  - INT and TERM are handled from before the repository or the network is read, in every mode. Before the tag the driver says nothing was tagged, pushed or published (in `--verify`, that it changes nothing and can be re-run); once the tag may exist it prints the way to finish. Bash runs a trap when the command running at the time returns, so a signal sent to the driver alone waits for that command, up to a download's 300 seconds. A signal the driver was started with ignored (a shell with job control off ignores INT in its background jobs, and `env -u` resets no signal) interrupts nothing: bash cannot trap it, and the run goes on to its own outcome.
  - Every `gh release` command, run or printed for finishing by hand, names its host (`-R github.com/<owner>/<repo>`), so a printed command works the same from an operator's shell whatever its `GH_HOST`.
  - Just before tagging, origin's main is read again and must still be the checked commit. After the push, origin's tag and GitHub's tag (read through the API, since origin's URL may be rewritten to a mirror) must both name it before anything is published. The assets are written from that commit, and `--verify` checks against it and requires both tags to name it.
  - In `--verify`, an HTTP error from the raw URL on every attempt, a missing asset, or a mismatch is a verify failure (1); a download or read that did not happen is exit 2.
  - Downloads are never written to disk: the raw URL and each release asset (`gh release download --pattern <name> -O -`) stream straight into the digest. Each side's status is read on its own, and the digest's first, since its failure closes the pipe and makes the download look like a retryable failure.
  - The temporary directory exists only for the two upload assets.
    - Its random name is chosen under the physical `TMPDIR`, and it is made with an atomic `mkdir` that runs with INT and TERM ignored. Only a directory that mkdir made is ever taken, and a signal arriving meanwhile is held and handled once the name is set.
    - Each directory's and file's inode is recorded as it is made, and one that cannot be read stops the run: before the tag for the directory, before the release for the assets. Cleanup removes an asset only while it is still that inode and still holds exactly the checked commit's blob (its git object id), never through a symbolic link, and then `rmdir`s the directories. So it removes only what it checked an instant before, and reports what it leaves; a shell cannot remove by inode, so that instant stays open.
    - A cleanup failure is reported beside the run's outcome and does not change its status.
  - The check-run and workflow-run lists must be as long as GitHub's own `total_count` for them, or the commit is refused rather than read as complete. GitHub caps the workflow-run search at 1,000 results, and lists check runs for the latest 1,000 check suites only, so a commit with more than 1,000 check suites is refused too.
  - The version check reads `shmutant.sh`'s one `SHMUTANT_VERSION=` line as text. It does not run `shmutant.sh` (that needs bash 5.3, and the driver runs on 3.2), so it proves the line, not that the line executes. The precondition is about that line, and the file is CI-tested.
  - `shmutant.sh` and `docs/integrating.md` are read through command substitution, which drops NUL bytes, so each read's length is held to git's size of the blob and a file holding a NUL is refused. `--verify` reads only `docs/integrating.md` as text, and a NUL there is a verify failure; it checks `shmutant.sh` by its digest, byte for byte. Bash drops a NUL past a script's first line when it runs it too, but the check is of the committed text, and a doc's reader sees the NUL.
  - In a partial clone, git older than 2.45 cannot be kept from lazily fetching, so the driver refuses it.
  - The script never deletes or moves a tag that may be on origin. When a cut fails or is interrupted after the tag may exist, it says what is left: the finish-by-hand commands when origin has this run's tag, or, when origin's tag names another commit or the published release does not verify, that the state needs inspecting first.
  - The version bump is `scripts/bump.sh <X.Y.Z | patch | minor | major>`, which rewrites everything the version check reads (SHMUTANT_VERSION, the install URL and version comment, README's dry-run example, and CHECKSUMS) and is tested by bumping the fixture and the repository's own files, then dry-running them. Given no version, `/release` picks one (shmutant.sh's when it is untagged, otherwise the next patch, or minor after a feat or breaking change) and, when main lacks it, lands the bump as a PR and waits for main's CI before the dry run (2026-10-19). A bare `/release` is what `/roadmap` emits once the release is ready, and it must reach the go-ahead without a hand step.
- placement: .claude/skills/release/SKILL.md; scripts/release.sh; scripts/bump.sh; test/release.sh; .github/workflows/ci.yml (`release` job); agents.toml [gates] `release-test`, [gates.cadence]; README "Releasing"
- reason:    a script can be shellchecked and tested where fenced shell in a skill cannot. No check reads a remote-tracking ref (origin and GitHub are asked directly), so the dry run needs no fetch.
- baseline-issue: n/a (release execution is project-owned)

## D7 — a unit ends a blocked background pool by process group, never by the subshell's pid
- date:      2026-10-07
- category:  project-delta
- unknown:   the `macos` job failed `self-mutation` on PR #14 twice (runs 37653275109 and 37690037322): the row 'the prepared root is read back by path after prepare' aborted with `exited 129, not 1`. Its witness, `t_prepare_cannot_redirect_its_own_capture`, ended its blocked pool by killing only the subshell. That stranded the command-substitution fork (adopted by launchd) and its `cat` in the suite's own process group, and the suite's sweep then froze both and KILLed them in one `kill`, the fork first. On macOS a process group in launchd's session is treated as newly orphaned when a member whose parent is launchd exits. If another member is still stopped at that moment, the kernel sends SIGHUP and SIGCONT to the whole group, which here held the suite and shmutant's run wrapper. Run as a launchd job (session 1), a model of this ends with status 129; with the sweep's kills spaced out, the real row aborts 3 runs out of 3, and the same copy run in an ordinary session is killed. The CI captures end exactly where the reproduction does, after the sweep's "left behind" listing.
- decision:  a unit that backgrounds a pool which may block starts it under `set -m` and ends it with `kill -KILL -- -<pid>`, as the units at the top of the pool section already did. Applied to `t_prepare_cannot_redirect_its_own_capture` and `t_verdict_timeout_without_an_identity`, the two units that killed only the subshell.
- placement: test/run.sh
- reason:    the strand is the cause the suite owns: a unit that leaves nothing behind gives the sweep nothing to freeze. With the fix, the reproduction that aborted 3 of 3 is killed 3 of 3 with nothing swept. Still open: the sweep freezes leftovers inside its own group, so a future unit that strands two or more processes, one adopted by launchd, can bring the same SIGHUP; no such unit is known.
- baseline-issue: n/a

## D8 — each unit runs in a process group of its own
- date:      2026-10-14
- category:  project-delta
- unknown:   the `macos` job failed `self-mutation` on `main` (run 38512825889, #42): the row 'the CLI has no signal handler around its plan subshell' aborted with `exited 129, not 1`. Its witness, `t_cli_interrupted_ends_its_workers_and_removes_its_workdir`, ended while the run it interrupted was still finishing. That left the CLI's sampler, which runs in the suite's own process group, adopted by launchd. The sweep froze it and KILLed it with the rest in one `kill`: the hazard D7 left open, from a unit D7 did not know. Run as a launchd job (session 1), a model ends with status 129 when a process launchd adopted exits while another member of its group is stopped. Three controls each survive: nothing stopped, only the exiting process stopped, or the pair in a group other than the suite's. In an ordinary session every variant survives. With the sweep's kills spaced, the real row aborts there with CI's verdict and CI's output, which stops after the sweep's "left behind" listing. The reproduction scripts and their results are in the pull request for #42.
- decision:  every unit runs in a process group of its own: job control for that spawn only, stdin from `/dev/null`, the subshell still tested by `||`. Nothing a unit leaves behind is then a member of the suite's group, which also holds shmutant's run wrapper, so the sweep's freeze and kill can hang up nothing of either. INT, TERM and HUP sent to the suite are passed on to the running unit's group, which a signal to the suite's group no longer reaches, and further ones are ignored until the unit is ended. The group's leader, the unit's wrapper, ignores those signals and so ends exactly when the unit does; the group is signalled only while that wrapper is a running job of the suite, so its number is never someone else's, and it is killed if the wrapper outlives three seconds. The unit is then swept as any unit is, and the sampler is killed if it has not stopped three seconds later. Only then does the suite end by the signal. The unit's directory is now made by the suite, which removes it after every unit and on an interrupt, whether or not the unit's EXIT trap ran. Each unit starts with those handlers cleared. Separately, the witness records every process of the run before its TERM and waits for them (`run_gone`, bounded). Whatever outlives the wait fails the unit and is killed by identity: frozen with its tree first when it is outside the unit's own group, unfrozen inside it, where a freeze could hang up the unit itself.
- placement: test/run.sh (`main`, `suite_signalled`, `run_gone`, `mk_cli_toy`, the witness, `t_suite_runs_each_unit_in_a_process_group_of_its_own`); README "Testing shmutant"
- reason:    the issue's own rule: a sweep that can hang up its suite is a harness defect, fixed in the sweep and not worked around in one unit. The group fixes it for every unit at once, as shmutant already isolates its plan subshell and each run. It keeps the freeze for every leftover and also covers a unit that freezes its own children. Not chosen: a sweep that never stops a member of its own group, which would give up the freeze for most leftovers (they are in the unit's group, which was the suite's); and a unit run in the foreground under job control, where a `^Z` breaks the suite's loop and the suite exits 0 with units unrun. D7's open item is closed.
- baseline-issue: n/a

## D9 — a check and its signal: what a freeze with no guard, the CLI's group and the guard's own end do
- date:      2026-10-23
- category:  project-delta
- unknown:   #53 asks that every process be stopped before the identity check that licenses its signal, or signalled in the same breath as a check that cannot go stale. #47 forbids a stop that no guard can undo, since a shell killed between the stop and the kill leaves it stopped for good. PR #66 left three sites where the two meet to the owner.
- decision:  the owner's call, given on 2026-10-23 in answer to three questions put during the /implement-issue run for #49 and #53 (each answer was the recommended option), and recorded in that run's pull request. (1) A freeze whose guard could not start still stops nothing. Its checks stay the last read before the one KILL, and the instant between them is the accepted cost of that path, which is reported `unsettled`. (2) `_shmutant_cli_end_group` ends the plan's group by a guarded freeze (`_shmutant_kill_tree_twice -g`), as a run's group is ended. Its holder is stopped before the check, a stop that reached a stranger is undone, and the guard covers a killed shell. This costs a guard's start at the end of every CLI run whose holder still lives. (3) `_shmutant_guard_close` kills a guard that did not stand down through the process group it leads, never by its pid as well. Its identity check stays unstopped: a guard stopped there and then orphaned would have nobody to end it.
- placement: shmutant.sh (`_shmutant_kill_tree`, `_shmutant_cli_end_group`, `_shmutant_guard_close`); docs/integrating.md (`SHMUTANT_TIMEOUT`)
- reason:    each choice keeps the #47 invariant (nothing stopped that nothing can undo) and closes every window that a guard can cover. The other sites #53 names close without a stop. A KILL names each pid once and the group last, its holder only through it, so no number that an earlier operand freed is named later in the same kill. A group is the run's only while its holder is among its members. Where the members cannot be read, the holder is taken to be in the group, as it is by construction, and is never also killed by number. `_shmutant_ps_end` kills by job (`kill %<job>`), which bash 5.3 sends with SIGCHLD blocked and only to a process its record shows alive. That holds once the substitution has turned job control on and off again before its jobs (`jobs.c` `kill_pid`, `set_job_control`), and has cleared every trap a caller's code could run between the job listing and the signal. Such a trap could reap the job and start another under its number.
- baseline-issue: n/a

## D11 — a unit feeds a guard that waits on its records' end through a pipe, never a FIFO
- date:      2026-10-25
- category:  project-delta
- unknown:   #70: `t_guard_waits_for_a_freezer_whose_elapsed_start_moved` failed on the `macos` job (runs 39655221496 on `main`, 40141433229, 40226033659 and both attempts of 40243044905 on PR #69): in its `step` or `blind` case the guard never acted once its records ended. A trace of the guard in launchd's session (3 failures in 40 runs, on `main` and on PR #69 alike) showed it going on with its one-second `read -t 1` looks after the unit closed the records' only writer, each look's process-table reads taking about 10 ms, and `lsof` showing no process left holding the FIFO but the guard's read end. In every failure the close landed within a millisecond of one of those reads timing out.
- decision:  the units feed such a guard its records through a pipe (`guard_on_pipe`, a process substitution), as a freeze does (a coproc's pipe), and `t_guard_on_pipe_shows_an_end_already_read` holds the helper to it. `_shmutant_guard` is unchanged: production never gives it a FIFO.
- placement: test/run.sh (`guard_on_pipe`, `t_guard_on_pipe_shows_an_end_already_read`, `t_guard_waits_for_a_freezer_whose_elapsed_start_moved`)
- reason:    two behaviours meet. bash 5.3's `read -t` waits in `pselect` and then reads; when what it read is an end-of-file with nothing before it, it checks its deadline again and, once that has passed, returns a timeout (`builtins/read.def`, `if (i == 0 && retval <= 0) check_read_timeout ();`), the end already consumed. And macOS shows a FIFO's end to `select` only until a `read` has returned it: probed on macOS 26.6 (Darwin 25.6), a FIFO with no writer is readable to `select` before the first read and never after it, while `read` still returns end-of-file; a pipe stays readable. So a `read -t` loop on a FIFO whose last writer closes at one of its deadlines times out for good, which a minimal script with no shmutant code reproduced (10 of 120 closes made near a one-second deadline). The unit closes the records about 3 s after the guard starts, on its third deadline, which is why it hit this so often. On a pipe the next look sees the end, so a lost one costs the guard one second. The guard's other units feed it a pipe already; `t_guard_takes_neither_a_reused_pid_nor_a_zombie_for_its_freezer` still uses a FIFO, but its guard ends by finding its freezer gone, never by its records' end. Not chosen: a longer bound, which the guard waiting for good outlasts; hardening the guard against an end taken for a timeout, which no production input needs. The `read -t` loops on FIFOs elsewhere (`sample_unit`'s read of its channel, `_shmutant_run_bounded`'s single reads) either keep a writer open (`<>`) or take a timeout and an end alike.
- baseline-issue: n/a
